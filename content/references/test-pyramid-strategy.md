어떤 앱을 처음부터 끝까지 훑는 수동 QA를 하고 나면, 늘 같은 결론에 도달한다.  
**"이 중 절반은 자동화 한 줄로 잡혔을 결함이다."**

테스트 코드가 전무했던 초기 B2B 멀티테넌트 SaaS(React + Supabase)의 dev 환경을 전 계층 탐색적으로 테스트하며 발견한 14건의 실제 결함을 바탕으로, 테스트 피라미드의 각 층이 실제로 무엇을 잡고 무엇을 놓쳤는지를 구조적으로 정리했다.

---

## 1. 수동 QA 결과: 방어선이 사람의 눈뿐일 때

관리자(Admin) · 팀 리더(Manager) · 일반 멤버(Member) 3가지 역할의 주요 화면을 돌며 네트워크, 콘솔, API를 직접 점검했다.

| 구분 | 건수 | 비고 |
| :--- | :--- | :--- |
| **릴리즈 차단 (P0)** | 3건 | anon 키로 전 테이블 조회/수정/삭제 가능, 평문 PIN 노출 등 |
| **주요 결함 (P1)** | 4건 | 워크스페이스 생성 후 DB 미반영(로컬스토리지에만 저장) 등 |
| **경미한 결함 (P2)** | 7건 | 웹 폰트 404, 접근성 미흡, 상태 초기화 등 |
| **자동화로 사전 차단 가능했던 결함** | **최소 5건** | 커밋/PR 단계에서 즉시 잡혔을 결함 |

초기 프로덕트는 대개 화면을 빠르게 붙이느라 테스트 피라미드의 아래층이 통째로 빈다.  
남는 방어선은 사람의 눈뿐이고, **사람의 눈은 릴리즈 직전에만 작동한다.**

## 2. 테스트 피라미드의 본질

```
        /\
       /E2E\        ← 소수, 느림, 비쌈, 불안정
      /------\
     /  통합   \      ← 중간
    /----------\
   /    단위     \    ← 다수, 빠름, 저렴, 안정
  /--------------\
```

마틴 파울러(Martin Fowler)가 정리했듯, 피라미드의 핵심은 비율 놀음이 아니다:
1. **위로 갈수록 느리고, 깨지기 쉽고, 원인 추적이 어렵다.**
2. **위층은 아래층이 이미 검증한 것을 다시 검증하지 않도록 설계해야 한다.**

| 계층 | 대상 | 실행 속도 | 실패 시 의미 | 전형적 도구 |
| :--- | :--- | :--- | :--- | :--- |
| **정적 (Static)** | 타입, 린트, 번들, 에셋 | 초 | 코드가 규칙을 어겼다 | TypeScript, ESLint |
| **단위 (Unit)** | 순수 함수 · 독립 모듈 | ms | 로직이 틀렸다 | Vitest, Jest |
| **통합 / 계약 (Contract)** | 모듈 + 실제 의존성 (DB, API) | 100ms ~ 수 초 | 컴포넌트 간 계약이 깨졌다 | Supertest, Testcontainers |
| **E2E** | 사용자 핵심 여정 전체 | 수십 초 | 제품이 동작하지 않는다 | Playwright, Cypress |

가장 흔히 누락되는 칸이 **정적(Static)**과 **계약(Contract)**이다.  
그런데 이번 사례에서 **P0 3건 중 2건이 정확히 이 두 칸에 속했다.**

## 3. 계층별로 실제 무엇을 잡았어야 했는가?

### 3.1 단위 테스트: 순수 로직의 회귀 방지
단위 테스트의 진가는 버그 탐지보다 **안전한 리팩터링**에 있다. 비즈니스 규칙이 클라이언트에 흩어져 있다면 단위 테스트가 유일한 방파제다.

#### (a) 날짜 및 주차 경계 계산
앱은 주차를 계산해 현재 주차에만 "리포트 작성"을 열어줘야 했다. 하지만 실제로는 미래 날짜(10/24–10/30)에서도 글 작성이 활성화되어 있었다.
```typescript
describe('주차 계산 로직', () => {
  it('미래 주차는 쓰기 가능 상태가 아니다', () => {
    expect(isWritableWeek(weekOf('2026-10-27'), new Date('2026-10-21'))).toBe(false)
  })
  it('주 경계(일요일 23:59 / 월요일 00:00)에서 라벨이 정확히 바뀐다', () => {
    expect(labelOf(new Date('2026-10-25T23:59:00+09:00'))).toBe('10월 4주차')
    expect(labelOf(new Date('2026-10-26T00:00:00+09:00'))).toBe('10월 5주차')
  })
})
```
날짜/시간대 로직은 사람 손으로 전수 검사할 수 없다. 단위 테스트가 유일한 답이다.

#### (b) 카운터 집계 불일치
한 화면에서 "등록 멤버 0명", 상단 탭에는 "멤버 (1)", 하단 요약 카드에는 "소속 멤버 1명"이 동시에 떴다. 세 컴포넌트가 제각각 집계하고 있었다.
```typescript
it('동일 데이터셋에서 모든 화면의 카운트가 일치해야 한다', () => {
  const stats = computeStats(members, teams)
  expect(stats.totalMembers).toBe(stats.perTeam.reduce((a, b) => a + b.count, 0))
})
```
집계 로직을 하나의 Selector 함수로 추출하고 단위 테스트를 걸면 이런 버그는 구조적으로 박멸된다.

### 3.2 통합 & 계약(Contract) 테스트: 가장 치명적인 구멍
이번 QA에서 터진 P0 2건은 **화면을 아무리 광클해도 보이지 않는다.** 브라우저가 아니라 API를 직접 찔러봐야 나온다.

브라우저 번들에 박힌 Supabase URL과 `anon key`로 REST 엔드포인트를 직접 찔러본 결과:

| 요청 | 응답 | 실제 의미 |
| :--- | :--- | :--- |
| `GET /rest/v1/users?select=*` | 200 OK | **이름, 역할, PIN 평문 전체 노출** |
| `GET /rest/v1/posts?scope=eq.manager_only` | 200 OK | **리더 전용 비공개 메모 전문 노출** |
| `GET /rest/v1/workspaces` | 200 OK | **초대 토큰까지 전량 노출** |
| `POST /rest/v1/posts` (엉터리 payload) | 400 (not 401) | **쓰기 정책 완전 개방 상태** |
| `DELETE /rest/v1/posts?id=eq.xxx` | 204 No Content | **삭제 정책 완전 개방 상태** |

로그인도 없이 `curl` 몇 줄로 전체 고객 데이터와 비밀번호를 털고 지울 수 있었다.  
원인은 **DB의 RLS(Row Level Security)가 꺼져 있거나 `using (true)`로 열려 있었고, 권한 검사를 오직 클라이언트 JS(`user.role === 'admin'`)에만 맡겨둔 것**이었다.

이 치명적 보안 구멍을 막는 계약 테스트는 1초도 안 걸린다:
```typescript
// tests/contract/rls.spec.ts
const ANON = process.env.SUPABASE_ANON_KEY!
const BASE = `${process.env.SUPABASE_URL}/rest/v1`

it('anon 키로 민감 유저 테이블을 조회할 수 없다', async () => {
  const res = await fetch(`${BASE}/users?select=id`, {
    headers: { apikey: ANON, Authorization: `Bearer ${ANON}` }
  })
  expect([401, 403]).toContain(res.status)
})

it('anon 키로 게시글을 임의 삽입할 수 없다', async () => {
  const res = await fetch(`${BASE}/posts`, {
    method: 'POST',
    headers: { apikey: ANON, Authorization: `Bearer ${ANON}`, 'Content-Type': 'application/json' },
    body: JSON.stringify({ probe: true }),
  })
  expect([401, 403]).toContain(res.status)
})
```
> **원칙**: 클라이언트 번들에 들어간 키는 누구나 열어보는 '공개 키'다. 그 키로 무엇을 할 수 있는지 검증하는 계약 테스트가 없다면 접근 제어는 아예 없는 것이다.

### 3.3 E2E 테스트: 끊기지 않는 사용자 여정
E2E의 역할은 로직 검증이 아니라 **"핵심 비즈니스 여정이 끝까지 이어지는가"**다.

이 프로덕트에서 E2E가 커버해야 할 핵심 여정은 딱 5개다:
1. 초대 링크 진입 ➔ 가입 ➔ 워크스페이스 대시보드 도달
2. 워크스페이스 생성 ➔ **새로고침 ➔ 데이터 영속 유지**
3. 게시글 작성 ➔ 피드 반영 ➔ 집계 카운트 증가
4. **리더 전용 비공개 글 ➔ 일반 멤버 계정에서는 미노출**
5. 권한 전환 ➔ 역할에 맞는 UI/메뉴만 렌더링

실제 QA에서 2번이 터져 있었다. UI에서는 워크스페이스가 생성된 것처럼 보였지만, Supabase에는 단 한 줄도 쓰이지 않고 브라우저 `localStorage`에만 임시 저장되고 있었다. 다른 브라우저나 기기에서 열면 데이터가 온데간데없었다.

```typescript
test('워크스페이스를 생성하면 새로고침 후에도 유지된다', async ({ page }) => {
  await page.goto('/')
  await createWorkspace(page, { name: 'Alpha팀', admin: '홍길동' })
  await page.reload()
  await expect(page.getByText('Alpha팀')).toBeVisible()
})
```
단 한 줄짜리 단언이 "DB 저장 누락"이라는 치명적 결함을 잡아낸다.

또한 4번처럼 권한에 따른 가시성은 **2개의 브라우저 컨텍스트를 동시에 띄워 교차 검증**해야 한다:
```typescript
test('관리자 전용 글은 일반 멤버에게 보이지 않는다', async ({ browser }) => {
  const adminContext = await browser.newContext()
  const memberContext = await browser.newContext()

  await createPost(adminContext, { scope: 'manager_only', content: '기밀 안건' })
  await expect(memberContext.getByText('기밀 안건')).toHaveCount(0)
})
```

### 3.4 정적 계층 (Static): 가장 저렴하고 빠른 안전망
테스트 코드라고 부르지도 않지만 가성비가 가장 좋다.

```bash
# 깨진 폰트 에셋 URL을 배포 전에 잡는 한 줄
curl -sI "https://cdn.jsdelivr.net/.../PretendardVariable.woff2" | grep -q "200" || echo "FAIL: 404 Font"
```
실제 QA에서 메인 variable 폰트 URL이 404를 내고 있었다. 브라우저가 시스템 기본 폰트로 폴백해 주니 사람 눈에는 안 띄고 콘솔 에러로만 남았다. 눈에 안 띄는 결함일수록 정적 검사가 잡아야 한다.

## 4. 이번 결함 14건의 계층별 역추적 매핑

| ID | 결함 내용 | 심각도 | 진작 잡았어야 할 계층 |
| :--- | :--- | :--- | :--- |
| **C1** | RLS 부재 — anon 키로 전 테이블 읽기/쓰기/삭제 가능 | **P0** | **계약 (RLS 테스트)** |
| **C2** | 비밀번호/PIN 평문 저장 및 클라이언트 단순 비교 | **P0** | **단위(해시) + 계약(인증 RPC)** |
| **C3** | 유효하지 않은 초대 토큰 진입 시 다른 조직 데이터로 폴백 | **P0** | **계약(스코프 격리) + E2E(초대 여정)** |
| **M1** | 조직/프로젝트 개설이 DB에 저장되지 않음 (로컬스토리지 누수) | **P1** | **E2E (새로고침 후 영속 검증)** |
| **M2** | 컴포넌트별 카운터 집계 수치 불일치 | **P1** | **단위 (집계 Selector)** |
| **M3** | 미래 주차/날짜에 쓰기 액션 활성화 | **P1** | **단위 (날짜 경계 함수)** |
| **M4** | 전역 데이터 삭제가 단순 확인창 1회로 실행 | **P1** | **E2E + 설계 리뷰** |
| **m1** | 웹 폰트 에셋 404 에러 | **P2** | **정적 (에셋 URL 스캔)** |
| **m2** | Realtime 웹소켓 초기 실패 후 재연결 지연 | **P2** | **통합 (스모크)** |
| **m3** | 폼 입력창 접근성(a11y) 라벨 누락 | **P2** | **E2E (Playwright a11y 단언)** |
| **m4** | 새로고침 시 필터 상태 초기화 | **P2** | **E2E** |

> **인사이트**: **P0 3건 중 2건은 화면을 보지 않는 계층(계약/정적)에서 잡힌다.**  
> 수동 QA는 화면을 보는 일이고, 화면은 이 백엔드 보안 결함들을 보여주지 않는다.

## 5. 피라미드가 붕괴된 안티패턴 2가지

### 1) 아이스크림 콘 (Ice Cream Cone)
```
   /-----------\
  /   수동 QA    \   ← 사람 갈아넣기
 /----------------\
/   E2E (불안정)   \
--------------------------
      단위 (전무)
```
릴리즈 주기가 "QA 가능한 사람의 일정"에 종속된다. 고쳤던 버그가 2주 뒤 다음 릴리즈에 똑같이 부활한다.

### 2) 모래시계 (Hourglass)
단위 테스트도 열심히 짜고 E2E도 몇 개 있는데 **통합/계약 계층이 텅 빈 형태**.  
아무리 순수 함수 단위 테스트를 촘촘히 짜도, `users` 테이블 RLS가 열려 있다는 사실은 단위 테스트가 알 수 없다. **경계를 넘는 지점은 경계에서 테스트해야 한다.**

## 6. 바로 써먹는 실전 CI 파이프라인 구성

```yaml
# 1단계: 커밋마다 (목표 30초 이내)
- tsc --noEmit                    # 타입 검증
- eslint .                        # 린트
- vitest run --coverage           # 순수 함수 단위 테스트
- node scripts/check-assets.mjs   # 에셋 404 검사

# 2단계: PR 생성 시 (목표 3분 이내)
- vitest run --project contract   # Supabase RLS 및 API 계약 테스트
- playwright test --grep @smoke   # 핵심 여정 3개 스모크

# 3단계: 머지 후 / 야간 정기 빌드
- playwright test                 # 전체 E2E 및 멀티 세션 권한 테스트
```

### Flaky(불안정한) E2E 테스트를 죽이는 4대 원칙
1. **재시도(Retry)로 덮지 마라**: 재시도는 버그를 숨기고 CI 신뢰를 갉아먹는다. 원인을 찾아서 고쳐라.
2. **시간 의존성을 격리하라**: `new Date()`를 직접 부르지 말고 주입 가능하게 설계하라.
3. **네트워크가 아니라 상태를 기다려라**: `waitForTimeout(2000)`은 죄악이다. `expect(locator).toBeVisible()`로 DOM 상태를 대기하라.
4. **테스트 데이터는 직접 만들고 직접 지워라**: 공용 dev DB를 여러 테스트가 공유하는 순간 서로의 발목을 잡는다.

## 7. 결론

테스트 피라미드는 "단위 테스트를 많이 짜라"는 원론적인 훈계가 아니다.  
**비용이 다른 검증 도구들을 적재적소에 배치해, 각 결함이 가장 저렴한 층에서 자동으로 걸러지게 만드는 시스템 엔지니어링이다.**

* **화면은 거짓말을 한다**: 새 프로젝트가 생성되었다고 예쁘게 렌더링되지만 DB에는 없다.
* **진짜 치명적인 구멍은 화면 밖에 있다**: RLS 누락, 권한 탈취, 평문 토큰은 클릭질로는 영원히 찾을 수 없다.
* **수동 QA는 회귀를 막지 못한다**: 이번에 잡은 P0 결함들은 다음 배포 때 또 터질 수 있다. 그 재발을 막는 것은 오직 CI 코드 한 줄뿐이다.
